**4. `client/src/components/Modal.js` — the one shared chrome (new file).**

Create the file exporting a default `Modal({ title, onClose, children })`. It renders a fragment containing `<div className="modal-backdrop" onClick={onClose} />` and, as its sibling, `<div className="modal" role="dialog" aria-modal="true" aria-labelledby={titleId} tabIndex={-1} ref={dialogRef}>`. Inside the dialog: a `.modal__header` holding `<h3 className="modal__title" id={titleId}>{title}</h3>` and `<button type="button" className="modal__close" onClick={onClose} aria-label="Close dialog">` whose visible child is the multiplication-sign character U+00D7. Then `{children}`. Generate `titleId` with React's `useId` so two dialogs can never collide on the same id.

Three behaviors beyond the markup, all required for the dialog to be operable without a pointer. First, a `useEffect` registering a `keydown` listener on `document` that calls `onClose` when `event.key` is the escape key, cleaned up on unmount — the backdrop and the close button both need a pointer or a tab-stop to reach, so without this a keyboard user has no exit at all. Second, a `useEffect` that focuses `dialogRef.current` on mount, so screen-reader and keyboard focus enters the dialog instead of staying behind it on the table. Third, capture `document.activeElement` on mount and call `.focus()` on it during cleanup, so closing returns the user to the row or button they opened from. These three are additions beyond the literal text of `06-UI-SPEC.md` §4, made because that section cites H3 user control as its reason for requiring two exits and the two it names are both pointer-reachable only; WCAG 2.1.1 and 2.4.3 require the keyboard equivalents. Record that reasoning in the file's own comment.

Render `children` and `title` as plain JSX children. Introduce no raw-HTML injection prop — see threat T-06-01.

**5. `client/src/components/Project.js` — the flattened table and the item-detail modal.**

Delete `LocationSection` entirely. Keep `AmbiguityNotice` exactly as it is — it is unused by the end of this task and gets its home in Task 2; leaving it defined is deliberate, not an oversight. Keep the `LOCATION_ORDER` constant. Import `Modal` from `./Modal.js`.

Add a presentational `InventoryTable({ rows, onRowClick })`. `rows` is an array of `{ item, location }` pairs. It renders `<table className="inventory-table">` inside `<div className="inventory-table-wrap">`, with a `<thead>` row of five `<th>` cells reading exactly `Location`, `Item`, `Capacity`, `Available`, `Freshness`, and a `<tbody>` mapping each row to `<tr className="inventory-table__row" key={...} onClick={() => onRowClick(row)}>`. The key must combine the location and the item key, because `itemKey` is only guaranteed unique within a location and the row set now spans all three. The five cells hold, in order: `{location}`; a `<button type="button" className="inventory-table__open" aria-haspopup="dialog">{item.itemName}</button>`; `{item.capacity}` with the numeric class; `{item.availability}` with the numeric class; and `<FreshnessBadge freshness={item.freshness} location={location} />`.

That button is the whole keyboard story, so do not give it its own `onClick`. A native button's Enter/Space activation dispatches a click event that bubbles to the `<tr>`, so the row's single handler serves pointer and keyboard alike — adding a second handler on the button would fire the row handler twice. Equally, do not move the handler onto the button and drop it from the row: the UI-SPEC requires clicking the row, not just the name, to open detail.

Pass `location` — the key the flattener iterated — to `FreshnessBadge`, never `item.location`. Phase 5 passed the section key here and Freezer's wording depends on it.

In `InventoryView`, add one piece of state: `const [openModal, setOpenModal] = useState(null)`, holding either `null` or an object with a `kind` field.
