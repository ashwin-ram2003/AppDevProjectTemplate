**1. `client/src/components/Modal.js` — document the shared dialog chrome.**

Add a four-part JSDoc block directly above the `Modal` function signature. The prose should say that `Modal` is the one shared dialog chrome used by both the Add Item form and the item-detail view, that its consistency across both is a Phase 6 success criterion rather than an implementation detail, and that it renders only what it is handed. Mark `Data source: props only` and carry the standard no-hard-coded-fallback line.

Document `@param {string} props.title` as the dialog's accessible name, rendered as its heading and referenced by the dialog's `aria-labelledby`; `@param {Function} props.onClose` as the handler invoked by all three exits — the close button, a backdrop click, and the Escape key — noting that the component owns no open/closed state of its own, so the caller decides what closing means; and `@param {React.ReactNode} props.children` as the dialog body.

State in the prose that focus enters the dialog on mount and returns to the previously focused element on unmount, so a later reader does not mistake the focus effects for incidental code and delete them. Keep the existing comment explaining the WCAG reasoning behind the Escape handler — merge it into this block rather than leaving two comments saying adjacent things.

**2. `client/src/components/Project.js` — document the two new components.**

Add a four-part block above `InventoryTable`. The prose should say it renders every location's items as one flat row set and performs no filtering, no sorting, and no fetching of its own — it renders exactly the array it is given, in the order given. That ordering statement matters for the same reason `BatchList`'s does: the server decides order, and re-sorting in the browser would show a household something untrue about its own inventory. Document `@param {Array} props.rows` as an array of `{ item, location }` pairs where `location` is the storage-location key the row was grouped under, noting explicitly that this key — not `item.location` — is what gets forwarded to `FreshnessBadge`, because the freshness wording differs per location. Document `@param {Function} props.onRowClick` as the handler called with a row pair when a row is activated by pointer or keyboard.

Add a four-part block above `LocationFilterTabs`. The prose should say it renders one pill per storage location plus an "All" entry, that it holds no state, and that the filtering it drives happens client-side over already-fetched data — it triggers no network request. Document `@param {string} props.active` as the currently selected value and `@param {Function} props.onChange` as the handler called with the newly selected value.

**3. `client/src/components/Project.js` — correct `InventoryView`'s prose only.**

`InventoryView`'s existing block is accurate about its three props, and those three props must not change — but its prose refers to a rendering structure this phase replaced. Update only the descriptive sentences so they describe the table-and-dialog structure, and update the document reference so it points at both the canonical design document and this phase's UI specification. Leave all three `@param` lines, the `Data source:` marker, and the no-hard-coded-fallback line byte-identical. Do not add a fourth `@param`; `InventoryView` still takes exactly three props.

`AmbiguityNotice`'s block stays exactly as it is — its single prop is unchanged and its prose says nothing about where it renders.

**4. Drift check on the four frozen components — read, do not edit.**

A drifted contract is a finding that needs a decision, because Track C audits DATA-01 and DATA-03 against these blocks rather than against the code — silently "fixing" a comment to match code that may itself have drifted would erase the evidence of which one moved.

Change no executable line in any file in this task.
