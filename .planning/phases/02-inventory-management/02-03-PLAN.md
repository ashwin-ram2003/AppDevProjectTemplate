<objective>
Finish item identity and make batch history visible. Restocking "Whole Milk" into the Fridge should land on the household's existing "Milk" rather than creating a second row nobody wanted, and opening that item should show each shopping trip as its own batch with its own dates.

Purpose: D-01 says every restock is its own batch and D-03 says item identity is name-matched per location. Plan 02-01 established the batch structure and the normalization half of matching. This plan lands the substring/prefix half, and with it the question D-03 leaves open — what happens when a name loosely matches more than one existing item. The answer has to be deterministic, because a household that sees its milk merge into its milkshake mix once will stop trusting the inventory.

Output: a complete, tested matcher with a stated ambiguity rule; restock wired through it; per-item batch detail in the inventory view.

Written test-first: matching is a pure function over a name and a list of existing keys, which is exactly the shape where the tests are cheaper to write than the implementation.
</objective>

<interfaces>
<!-- Added to the itemIdentity module established by plan 02-01. -->

findMatchingItemKey(normalizedName, existingKeys) -> str or None

  Resolution order, first rule that applies wins:
  1. exact  — normalizedName is in existingKeys            -> return it
  2. loose  — candidates are the keys where normalizedName is a substring of the key
              OR the key is a substring of normalizedName
              exactly one candidate                        -> return it
              two or more candidates                       -> raise AmbiguousItemMatch
  3. none                                                  -> return None

  AmbiguousItemMatch carries the colliding candidate keys so the caller can report them.

Caller contract in hardwareDatabase.addBatch:
  - existingKeys is scoped to ONE householdId and ONE location, never wider
  - None      -> create a new item, itemName = the raw name as typed
  - a key     -> append the batch to that item, leaving its stored itemName unchanged
  - Ambiguous -> create a new item (the deterministic no-guess outcome), and include the
                 colliding keys in the response so the UI can say why nothing merged
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Flask REST API | `itemName` is free text from an untrusted client and now flows into a database query used to find match candidates. |
| one household's data → another household's data | The matcher reads existing item keys; a query scoped too widely would let one household's restock see or touch another's items. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-02 | Tampering | the candidate-key query inside `hardwareDatabase.addBatch` | high | mitigate | `itemName` is coerced through `normalizeItemName`, which raises on any non-string input, before it is used; the resulting value is compared in Python with plain string containment and is never embedded in a pymongo filter document, so an attacker-supplied object such as a query operator cannot become part of a query. The candidate query filters on `householdId` and `location` only, both of which are validated first. Asserted by Task 2's acceptance criteria and the two-household test. |
| T-02-12 | Information disclosure | cross-household match candidates | high | mitigate | The candidate list passed to `findMatchingItemKey` is scoped to one householdId and one location; Task 2's behavior block includes a two-household test proving neither household's restock merges into or reveals the other's items. The route still calls `assertHouseholdMember` first (plan 02-01, T-02-01). |
| T-02-13 | Denial of service | loose matching scans every item key in the location | low | accept | The candidate set is one household's items in one of three locations — tens of short strings, compared with plain containment. There is no regular expression built from user input, so there is no catastrophic-backtracking surface. Revisit only if a single location exceeds a few hundred distinct items. |

**ASVS level 1, block on high.** Both high-severity threats sit on the primary browser→API boundary and are mitigated with named, tested controls. T-02-13 is accepted with the rationale above.

**Package legitimacy:** this plan installs nothing. Task 1 explicitly forbids adding a matching library, and its third verify gate asserts none was imported.
</threat_model>
