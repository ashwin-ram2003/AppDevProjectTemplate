<objective>
Give every item a freshness flag computed from its own dates, using three genuinely different rule-sets — one per location — rather than one flat best-by comparison.

Purpose: INV-05 reads like a single rule, but CONTEXT.md D-09, D-10, and D-11 record three. The Freezer rule is not a weaker version of the Fridge rule; it models a different physical process (freezer burn, a quality signal computed from the freeze date) and deliberately does not consult a best-by date at all. Getting this wrong in either direction produces either false alarms on dry staples or "throw it out" advice about perfectly safe frozen food.

Output: a pure, fully-tested freshness module; freshness annotations on every batch and item returned by the inventory API; a badge in the inventory view that says the right thing for each location.

Written test-first: these are pure functions with exact input-to-output pairs and sharp boundaries, which is the case where a failing test written before the code is cheapest and most valuable.
</objective>

<!-- Contract this plan adds to the item shape established by plan 02-01. -->

Freshness values (string constants exported from server/freshness.py):
  FRESH          = "fresh"
  EXPIRING_SOON  = "expiring_soon"
  EXPIRED        = "expired"
  UNKNOWN        = "unknown"

SEVERITY_RANK maps each value to an int so "worst of" is a max over a total order:
  UNKNOWN 0 < FRESH 1 < EXPIRING_SOON 2 < EXPIRED 3

Thresholds (named constants, never inline numbers):
  FRIDGE_EXPIRING_SOON_DAYS      = 3
  FREEZER_EXPIRING_SOON_MONTHS   = 6
  FREEZER_EXPIRED_MONTHS         = 12

computeBatchFreshness(location, purchaseDate, bestByDate, today) -> one of the four constants
computeItemFreshness(location, batches, today)                   -> one of the four constants

Added to the API response documented in 02-01 (both are computed, never stored):
  item.freshness        one of the four constants
  item.batches[].freshness   one of the four constants
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Flask REST API | The client could try to influence what "today" is, or what freshness an item reports. |
| server freshness rules → household member's decision to eat or discard food | The flag is advice a person acts on; a wrong framing here causes real-world harm (wasted food or eaten spoiled food). |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-02-07 | Tampering | freshness computation in `getItemsByLocation` | medium | mitigate | `today` is computed server-side from `datetime.date.today()` inside the read path; no request parameter or body field can supply it. | T-02-11 | Information disclosure | freshness values for another household's stock | high | mitigate | Inherited, not re-implemented: every freshness value is produced inside `getItemsByLocation`, reachable only through `getHouseholdInventory`, which calls `assertHouseholdMember` first (plan 02-01, T-02-01).
