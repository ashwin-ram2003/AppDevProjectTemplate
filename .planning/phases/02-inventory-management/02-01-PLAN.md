<!-- The REST contract this plan establishes. Later plans in this phase extend it; they do not redefine it. -->

Item document (collection `Items`, one document per household + location + itemKey):
  _id                ObjectId
  householdId        str
  location           str        one of "Pantry" | "Fridge" | "Freezer"
  itemKey            str        normalized name (itemIdentity.normalizeItemName)
  itemName           str        display name — the spelling first used for this itemKey
  batches            list of    { batchId: str, quantity: int, purchaseDate: "YYYY-MM-DD",
                                  bestByDate: "YYYY-MM-DD" or None, createdAt: ISO-8601 str }
  reservations       list       [] in this plan; populated by plan 02-04
  capacity           int        maintained sum of batch quantities (units physically on hand)
  reservedQuantity   int        maintained sum of reservation quantities; 0 in this plan

Derived on read, never stored:
  availability       int        max(capacity - reservedQuantity, 0)
  freshness          str        absent in this plan; added by plan 02-02

Household document (collection `Households`) — Track A owns writes. Track B reads only the
`users` array (list of userId strings) and the `householdId` field, via assertHouseholdMember.

GET /api/inventory?householdId=<id>&userId=<id>
  200 -> { "householdId": str, "locations": { "Pantry": [item], "Fridge": [item], "Freezer": [item] } }
  400 -> { "error": "missing_parameter", "field": str }
  403 -> { "error": "not_a_household_member" }

POST /api/inventory/restock
  body  { householdId, userId, location, itemName, quantity, purchaseDate, bestByDate }
  201 -> { "item": item }
  400 -> { "error": "invalid_input", "field": str }
  403 -> { "error": "not_a_household_member" }

Error envelope for every inventory route: a JSON object with an "error" string key.
</interfaces>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 2: Choose where household inventory is stored</name>
  <decision>Does the food-item inventory live embedded inside each household document, or in its own `Items` collection keyed by householdId?</decision>
  <context>
    This is the one-way door of the whole track. Once Tracks A, C, and D read or deploy against this shape, changing it is a data migration, not a refactor — and it is exactly the coordination point ROADMAP.md flags ("agree on the household document's item-stock shape before both tracks start writing to it", board item TD-03).

    CONTEXT.md D-01 fixes the per-item shape (batches with their own purchase and best-by dates, capacity/availability derived as sums). What is NOT yet decided is where that structure physically lives.
  </context>
  <options>
    <option id="separate-items-collection">
      <name>Separate `Items` collection (recommended — the tasks below are written for this)</name>
      <pros>One document per household+location+item, so a consume can be a single conditional atomic update guarded on capacity rather than a read-modify-write of a large nested array. Track A keeps exclusive write ownership of the household document, which removes the write contention the roadmap flags as this project's main merge risk. Per-item documents stay small as batch history grows.</pros>
      <cons>Adds a second collection, so ROADMAP.md's "inventory lives in the household document" wording needs a one-line correction. An inventory read touches two collections (Households for the membership check, Items for the stock).</cons>
    </option>
    <option id="embedded-in-household">
      <name>Embed an `inventory` array inside the household document</name>
      <pros>Matches ROADMAP.md's current wording exactly. A single document read returns the household and all its stock together.</pros>
      <cons>Track A and Track B then write to the same document concurrently. Updating one batch inside an array nested in an array requires positional operators that are awkward to guard atomically, so the overbooking guard (TD-04) becomes harder to make race-safe. The household document grows without bound as batch history accumulates.</cons>
    </option>
  </options>
  <resume-signal>Select: separate-items-collection or embedded-in-household. If embedded-in-household is chosen, keep every function signature, route path, request body, and acceptance criterion in this plan unchanged — only the collection the documents are read from and written to changes.</resume-signal>
</task>
